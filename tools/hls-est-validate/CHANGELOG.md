## 2026-10-09 — hls-est: fold constant bank indices in banking; fast resource-bound scheduling for large bodies
- **Commit:** the commit titled `hls-est: fold constant bank indices in banking; fast resource-bound scheduling for large bodies` (this entry is part of it)
- **Files:** lib/Dialect/Resource/Passes/MemoryBankModified.cpp, lib/Dialect/Resource/Passes/AffineToLoopScheduleModified.cpp, include/circt/Conversion/Passes.td, lib/Analysis/DependenceAnalysis.cpp, include/circt/Analysis/DependenceAnalysis.h, lib/Dialect/Resource/Passes/CyclicSchedulingAnalysisModified.{cpp,h}, test/hls-est/Passes/banking_constant_operand.mlir, test/hls-est/Passes/fast_schedule.mlir; deleted the stale, checked-in `include/circt/Conversion/Passes.h.inc` (a Sep-18 generated copy that shadowed `build/clion/include/...` because `-I include` precedes the build include dir; with it present no new pass option could be compiled).
- **What:** performance only; no estimate is meant to change.
  1. *Banking* (`--memory-banking-bram`): `BankAffineLoadPattern`/`BankAffineStorePattern` now call `canonicalizeMapAndOperands` after composing the access map, so an SSA-constant index (what `--auto-pipeline-unroll` leaves for the first unrolled iteration, `%buf[%i, %c0]`) folds to a constant bank instead of being treated as rotating (f loads + f-1 `arith.select`, or f `affine.store_enable`). The same decision is also made through a stepped loop counter (`%buf[%j + 1]` with step 4 pins bank 1), which is how `--infer-vitis-split-array` already classifies it, so both passes agree on which accesses rotate. On atax the banked IR went from 252 selects + 192 store_enables to none.
  2. *Scheduling* (`--convert-affine-to-loopschedule`): new option `fast-threshold=N` (default 150). A loop whose modulo problem has more than N resource-limited ops is scheduled by a greedy resource-bound modulo list scheduler: II starts at ResMinII = max over resources of ceil(uses/limit), resource-free ASAP times are longest paths in the constraint graph (edge weight latency − distance·II; a positive cycle bumps II, which is what the simplex does when it raises its parameter T), ops are placed in a topological order of the distance-0 edges (ties by program order) at the first modulo-reservation-table slot from their ASAP time, every edge including back edges is re-verified and a violation bumps II. `fast-threshold=0` uses it for every loop; on failure it falls back to the simplex. Small bodies keep `ModuloSimplexScheduler`. New option `cse` (default on) merges duplicated side-effect-free ops (per-access index arithmetic) before the problem is built, never memory ops; this replaces an `OpPassManager` with CSE that was built but never run.
  3. *MemoryDependenceAnalysis* (lib/Analysis): accesses are grouped by memref before pairs are enumerated (the all-pairs loop over ~9000 accesses built two `MemRefAccess` objects and walked the loop nests for ~10^8 cross-memref pairs); pairs whose index along some dimension is a different constant skip the test; the Fourier–Motzkin test is memoized on everything it depends on (composed maps/operands, enclosing blocks, depth, program order), so the 128 identical `tmp1[i][j]` accesses per bank of an unrolled `+=` reduction cost one test instead of 16k; only actual dependences are recorded (every consumer filters on `hasDependence()`); `replaceOp()` re-keys the destination properly (the old code assigned the new key through the map iterator, which leaves the entry in the old key's hash bucket where a lookup by the new op cannot find it) and retargets sources through an inverted index instead of rescanning every list. `CyclicSchedulingAnalysis::analyzeForOp` takes the analysis by reference instead of copying it per loop. `--debug-only=memory-dependence-analysis` prints pair/memo/test counts and the time.
- **Why:** CLAUDE.md working loop needs the canonical pipeline to finish; atax took 9–16 min and every 64×64 kernel timed out. Verified with `--mlir-timing` on the split pipeline: banking itself was 0.007 s but its rotating expansion made the scheduler's input 4–64× larger; on gemm the dependence analysis then ran 1.04M FM tests (144 s) and `replaceOp` rescanned 1M records per lowered op (~60 s). No Vitis behaviour is modelled differently (VITIS_NOTES.md untouched).
- **Effect:**
  - Base pipeline (`--affine-loop-normalize --memory-banking-bram --convert-affine-to-loopschedule --bram-analysis`) on all 42 `test/hls-est/Estimation` inputs, before vs. after: 41 identical (rc and Total BRAM); the 42nd, basic/arraypartition_complete, timed out at 300 s before and now gives 0 BRAM in 21 s. Wall sum 333 s → 23 s. `fast-threshold=0` vs. default: 42/42 identical totals (wall 23 s → 2.7 s). `cse=false` vs. default: identical totals. `--bram-debug` invariance script: 35 PASS / 7 ERR (same failures in both modes, as before plus the un-timed-out case).
  - Canonical pipeline on fresh cgeist output (`~/hls-est-work/mlir`, 8 parallel jobs on a loaded machine), old → new binary: polybench atax >900 s → 0.2 s (67), bicg >900 s → 0.2 s (68), gemm >900 s → 14 s (328), gesummv abort after 460 s (SimplexSchedulers.cpp:1174 assertion) → 0.3 s (134), k2mm >900 s → 24 s (464), k3mm >900 s → 28 s (408), mvt abort → 0.9 s (14), syr2k >900 s → 26 s (576), syrk >900 s → 11 s (320); polybench_pragmas (all 7 kernels >300 s before): bicg 2.3 s (8), gesummv 0.9 s (16), k2mm 2.3 s (56), k3mm 3.0 s (56), mvt 2.9 s (8), syr2k 1.2 s (56), syrk 0.8 s (32). Every polybench/polybench_pragmas case is now < 60 s.
  - Greedy vs. exact on the large bodies (`fast-threshold=1000000` forces the simplex): atax 67 = 67, bicg 68 = 68 (23 s vs 0.2 s); gesummv and mvt: the simplex aborts (pre-existing assertion in its II-bump path) where the greedy gives 134 and 14; gemm/k2mm/k3mm/syr2k: the simplex exceeds 600 s. So no case where both finish differs. Known heuristic difference, documented in fast_schedule.mlir: the simplex fixes ops in least-slack order and can raise II above ResMinII when a successor was fixed before the last of its port-contending predecessors (II 4 instead of 3 on a 3-reads-per-iteration loop); the greedy scheduler keeps ResMinII.
  - Harness subset (`run_hlsest.py --datasets polybench,polybench_pragmas,forgebench,machsuite,spector_hls,vitis_examples -j 8 --timeout 120`, canonical pipeline): status ok 63 → 75, `hls-est timeout 120s` 15 → 1 (forgebench/diff_orders_module), crash 9 → 11 (forgebench/conv_block_module and conv_block_op1 now reach the pre-existing `Type::getIntOrFloatBitWidth` assertion of the conv_* family instead of timing out first). polybench: 5 timeouts → 0. `compare.py`: 73 compared, 31 exact, |err| 8144 against the partial results/vitis.json.
  - Lit `test/hls-est`: 49 tests, 21 passed (19 + the two new ones), 24 unresolved (no RUN line, pre-existing), 4 failed (the pre-existing forgebench CHECK-BRAM tests). Output is run-to-run deterministic (5 inputs × 3 runs identical, before and after).
- **Reverted?:** no

## 2026-10-09 — hls-est: debug mode review fixes
- **Commit:** 93dba77f4 (branch `hls-est-vitis-match`); this entry: the following changelog-only commit
- **Files:** lib/Dialect/Resource/Passes/BRAMAnalysis.cpp, lib/Dialect/Resource/Passes/MemoryBankModified.cpp, lib/Dialect/Resource/Interfaces/MemoryInterface.cpp, include/circt/Dialect/Resource/Interfaces/MemoryDS.h, test/hls-est/Passes/bram_debug_provenance.mlir (new), test/hls-est/Passes/bram_debug_status.mlir (new), test/hls-est/Passes/bram_debug_text.mlir, tools/hls-est-validate/CHANGELOG.md
- **What:** the six findings of the review of fa522b385. (1) A memref with a dynamic extent gets `status = "dynamic_shape"` (the status existed but was unreachable; such memrefs were reported as `zero_size`). (2) An unwritable `--bram-debug-json` path is a pass failure: the stdout report is still printed in full, then `error: bram-debug-json: cannot write '<path>': <reason>` and a non-zero exit (was a warning with exit 0, detectable only by the file's absence). (3) `hls.partition` on banks records the effective `kind`, `factor` and 1-based `dim` that banking applied (a `complete` entry without a factor shows the dimension extent; a Vitis `dim = 0` pragma shows `dim = 1`); before, `dim` was the pragma text next to an effective `factor`. (4) A partitioned array without `polygeist.varname` gets `hls.bank_of = "<unnamed@file:line:col>"`, or `"<unnamed#k>"` without a location (k = its position among the function's storage declarations), so its banks aggregate in the JSON, the text report and compare.py (before: no `hls.bank_of`, each bank keyed by its id). (5) The previous entry now records its commit hash. (6) The threshold quoted in `excluded_small` reasons is `kBRAMPromotionBits`, moved to `MemoryDS.h` and used by `contributesToBRAMCost`, so the explanation cannot go stale; the wording is `size N bits <= 1024-bit BRAM promotion threshold; kept in LUTRAM/FFs`. Not changed (informational findings of the review): get_global / function-argument banking paths remain unreachable from `runOnOperation`, there are still no entries for top-level arguments or for arrays removed by earlier passes, and `bank_math.replication` is still 1.
- **Why:** code review of fa522b385; no new Vitis evidence involved.
- **Effect:** no estimate changes. `check_debug_invariance.sh` (60 s timeout), lit pipeline (--affine-loop-normalize --memory-banking-bram --convert-affine-to-loopschedule --bram-analysis): 42 cases, 35 PASS, 0 FAIL, 7 ERR (tool failed identically with and without the flags: exit 1 chstone_xilinx/sha, flowgnn_xilinx/gin, flowgnn_xilinx/pna, machsuite/spmv_crs, spectorhls/matrix_multiplication; abort machsuite/stencil2D, spectorhls/sobel_filter_y; all pre-existing). Default pipeline: (--affine-loop-normalize --auto-pipeline-unroll --infer-vitis-split-array --memory-banking-bram --convert-affine-to-loopschedule --bram-analysis, run concurrently with another agent's sweep on the same machine): 42 cases, 31 PASS, 0 FAIL, 11 ERR = 5 x hls-est timed out at 60 s in both runs (forgebench/attention_op_p1, forgebench/tiled_attn_module, forgebench/tiled_attn_p1, forgebench/tiled_attn_p2, machsuite/fft_transpose), 4 x exit 1 (chstone_xilinx/sha, flowgnn_xilinx/gin, flowgnn_xilinx/pna, spectorhls/matrix_multiplication), 2 x abort (machsuite/stencil2D, spectorhls/sobel_filter_y); every case that produced a report produced the same stdout with and without the flags, and its JSON total equalled the report total. ## 2026-10-09 — hls-est: --bram-debug / --bram-debug-json explanation mode; bank provenance attributes
- **Commit:** fa522b385
- **Files:** lib/Dialect/Resource/Passes/BRAMAnalysis.cpp, lib/Dialect/Resource/Passes/MemoryBankModified.cpp, lib/Dialect/Resource/Passes/InferVitisSplitArray.cpp, test/hls-est/Passes/bram_debug_json.mlir, test/hls-est/Passes/bram_debug_text.mlir, tools/hls-est-validate/check_debug_invariance.sh
- **What:** two global `llvm::cl` options (so they attach to any pipeline string): `--bram-debug` prints, to stderr after the normal report, one block per memref (id, name/varname, kind, loc, shape, element bits, words; status and exclusion reason; partition kind/factor/dim/source/bank index/count and the inference reason; every access with its scope, II, stage and store_enable flag; per-scope and combined port demand; the RAM type and why; the bank math: bits/BRAM, max width, config width, width tiles, depth/block, depth tiles, replication, blocks) and a summary sorted by BRAM; `--bram-debug-json=<path>` writes the same facts as JSON (`version`, `total_bram`, `functions`, `memrefs[]`, `summary[]`), which `compare.py` consumes. Memory banking now stamps every bank with `polygeist.varname`, `hls.preserve`, `hls.bank_of`, `hls.bank_index`, `hls.bank_count`, `hls.partition = {kind, factor, dim, source}` (the original pragma entry's fields; `source = "pragma"` when the entry has none) and `hls.partition_reason`; `infer-vitis-split-array` records `hls.partition_reason = "pipelined loop [lb..ub step s) @ loc: R reads/W writes per iteration, target II n, factor f (kind, dim d) (port-limited II a -> b)"`. No pass reads any of these attributes. Globals' accesses are not attributed (memref.global has no SSA result); the JSON says so in `ram_reason` instead of inventing data.
- **Why:** CLAUDE.md Step 3; the per-array JSON is the main debugging signal for Vitis mismatches (totals hide offsetting errors). Before this, banks created by `memory-banking-bram` had no attributes at all, so nothing could name them after the original alloca was erased.
- **Effect:** no estimate changes. `check_debug_invariance.sh` (every test/hls-est/Estimation/**/*.mlir, base pipeline, with vs. without the flags, stdout diffed): default pipeline (--affine-loop-normalize --auto-pipeline-unroll --infer-vitis-split-array --memory-banking-bram --convert-affine-to-loopschedule --bram-analysis, 60 s timeout): 42 cases, 17 PASS, 0 FAIL, 25 ERR (hls-est timed out or failed identically in both runs: 19 timeouts, 4 x exit 1, 2 x abort); lit pipeline (--affine-loop-normalize --memory-banking-bram --convert-affine-to-loopschedule --bram-analysis): 42 cases, 34 PASS, 0 FAIL, 8 ERR (1 timeout, 5 x exit 1, 2 x abort). No case produced a different stdout or a JSON total different from the report total. Lit `test/hls-est`: 45 tests, 17 passed (including the two new ones), 4 failed, 24 unresolved; the 28 non-passes are pre-existing: 24 Estimation inputs have no RUN line (unresolved) and 4 (forgebench/activation_op1, tiled_attn_p1, tiled_attn_p2, tiled_attn_module) pipe into FileCheck -check-prefix=CHECK-BRAM without defining any CHECK-BRAM: line.
- **Reverted?:** no
