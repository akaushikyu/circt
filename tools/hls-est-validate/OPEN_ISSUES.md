## O18. ROM conversion and stored-value width narrowing are not modelled (filed 2026-10-10, T4 entry)
- **Symptom:** dead_globals.md R3/R4 (VITIS_NOTES.md N1a "Constant-initialised arrays"): an array filled by one unconditional full-range constant loop becomes a ROM of the constant's width (all-zero: no array), and an array that only ever receives constants is narrowed to their bit range (`512x1`, LUTRAM). hls-est uses the declared width: on cgeist output of the 22 dead_globals kernels (`~/hls-est-work/t4/dg/`, no-split pipeline) dg_c_const0, dg_c_const01, dg_c_const0_cond, dg_c_const0_x2, dg_d_int0, dg_d_int0_single are 1 where Vitis has 0, with and without the T4 cleanups (cgeist itself already deletes their dead producer arrays).
- **Fix:** a value-range pass on stored values (at least "all stores are constants" -> width = bits of the constants) before `--bram-analysis`, plus the R3 precondition kernels of dead_globals.md section 5 (partial range, stride 2) before encoding the ROM conversion.

## O17. Promoting globals to locals exposes three gaps the "global = one RAM_1P" rule hid (filed 2026-10-10, T4 entry)
- **Symptom:** with `--promote-globals-to-allocas --bram-attribute-globals` (MEMOS.md M5) the forgebench file-scope arrays get the alloca treatment (banking per pragma, port demand, RAM_1WNR replication), which is what Vitis does (N1a R6), but three other differences then show up per array:
  1. *Callees Vitis keeps as modules (O10).* cgeist inlines them, so the weight arrays they read sit in the top's pipelined loops and get up to 15 RAM_1WNR copies: attention_op_p2/p3 BRAM_weights_q/k/v 64x64x16 are 4 BRAM each as globals (= Vitis, plain `RAM_AUTO_1R1W` read from the `grouped_multihead_attention` instance) and 60 each when promoted (15 copies; design 18 -> 202 under the exact shim, Vitis 24); attn_breakdown_* Q/K/V_weight_buffer and embedding_buffer_1 1 -> 15 each (Vitis 1, read from the `top_A` instance); Llama_GPT_module / gpt_transformer_p1 / llama_transformer_p2 FF_weights_2 4 -> 24 (6 copies). Vitis does not replicate an array whose readers are in a sub-module (the array lives in the parent and the callee reaches it through ports) - unconfirmed as a rule, consistent with all of these.
  2. *Partition pragmas on two dimensions.* `hls.array_partition` with two entries (cyclic 16 on dim 1 and on dim 2) is banked on the first entry only (`parsePartitionSpec` / `--memory-banking-bram`): vec_mtx_p1 BRAM_1[16][64] becomes 16 banks of 1x64 (1 BRAM each under the exact shim) where Vitis makes 256 four-word banks (registers, no memory row).
  3. *Partition pragmas on a callee's array parameter* (mult_op_p2 `mmv_ij`: input_A dims 1 and 2, input_B dim 1) apply to the caller's global in Vitis (no memory rows); after cgeist's inlining hls-est sees no pragma on BRAM_1 / BRAM_2 (cause unconfirmed: whether the attribute is dropped by the inliner or never attached).
  Under the scalar shim every promoted array is also 2x wide (O6).
- **Effect:** these designs were close or exact only because the old rule ignored the globals' accesses and pragmas (mult_op_p2 and vec_mtx_p1 exact by cancellation with the then-missing m_axi adapter). Fix 1-3 before proposing the promotion.

## O16. Dead-memory elimination and the integer folds need integer-backed ap_fixed (filed 2026-10-10, T4 entry)
- **Symptom:** `--vitis-fold --dead-memory-elimination` remove what Vitis removes only when the frontend gives the fixed-point arithmetic as integers. With the harness's scalar shim (ap_fixed = f32) and `--shim exact` (f16) the attention scale is `1.0f / sqrtf(16)` (or 0.25 in f16), nothing folds, Q and K stay (forgebench attention_op_p1: 406 / 203 BRAM, Vitis 73). With the `exactclass` shim (raw `_BitInt` members, `--scalar-wrapper-abi`, c733e425e, opt-in) cgeist emits `arith.divsi 4194304, 0` and the T4 cleanups plus `--bram-attribute-globals --bram-maxi-adapters` give **73 = Vitis**, per array (BRAM_attn_input 2, BRAM_weights_v 64, BRAM_1 2, V 2, scores 1, mem1 adapter 2; Q, K, BRAM_weights_q, BRAM_weights_k eliminated - N1's a.o.1 list). On the 22 C-int dead_globals kernels the cleanups change nothing: cgeist already deletes those dead arrays.
- **Subset under the exactclass shim** (harness `--shim exactclass`, runs `~/hls-est-work/t4/xc_*.json`): fold + DME + `--bram-maxi-adapters` make attention_op_p1 (73), tiled_attn_p1 (73), tiled_attn_p2 (23) exact; tiled_attn_module goes 304 -> 110 against Vitis 270 because Vitis keeps BRAM_A2/A3/B2/B3 as `RAM_AUTO_0R0W` memories (160 BRAM, counted although nothing reads them): there the `load_*` functions that write them are not inlined (8 `call @load_*` at a.o.1, none in attention_op_p1 / tiled_attn_p1), so the arrays escape into a call - cgeist inlines them (O10) and DME removes the arrays. dg_d_apfixed16 under exactclass + T4 gives 2 = Vitis (V 1, scores 1; Q, K eliminated).
- **C-int division by a constant 0 (T4 review, VITIS_NOTES.md N1a "Division by a constant 0"):** Vitis makes int `x / 0`, `x % 0` and unsigned `x / 0u` undef (the output store and every array feeding the expression disappear), while ap_fixed `x / 0` and unsigned `x % 0u` are 0. `--vitis-fold` folds all four integer ops to 0 because under the exactclass shim an ap_fixed division is an `arith.divsi` like a C one. For the undef cases hls-est therefore keeps the other operands of the expression: `dg_d_fold_divrem0` 12 BRAM vs Vitis 6 (a_sdiv, a_srem, a_udiv kept). Distinguishing the two needs the frontend to mark the fixed-point division (or emit `ub.poison` for C division by a constant 0); no benchmark in the subset divides by a constant 0 in C int arithmetic.
- **Decision:** with M2/M3 (which shim the harness uses) and M5.

## O15. Assignable bit / range selects do not compile with the `exactclass` shim (filed 2026-10-10, route A entry)
- **Symptom:** `x.range(h, l) = v`, `x(h, l) = v`, `x[i] = b`, `(a, b) = v` are lvalue uses of Vitis' reference-proxy classes (`ap_range_ref {T& d_bv; int l, h;}`, `ap_bit_ref`, `ap_concat_ref`, `af_range_ref`). `shim/exactclass` returns `const` values from `range()` / `operator()` / `operator[]` / `bit()` / `operator,`, so these lines are clang errors (`no viable overloaded '='`), loudly instead of silently wrong. In the 7-dataset route-A run (`/tmp/routeA.json`) this stops **23 designs (14 with Vitis ground truth)**: all 11 soda (`dram_*_buf(255, 240) = Reinterpret<ap_uint<16>>(...)`), accelerators Mask-Net_dataset and SkyNet_dataset (`DATA.range(FM_RG + 16*c, 16*c) = d.range(FM_RG, 0)`), vitis_examples/01 fixed_point_sqrt (`fxp_sqrt.h:101 result.range(W2-1,0) = ap_uint<W2>(q >> 1)`), 9 class_ece8893_spring_2025 lab designs (`temp.range(16*(jj+1)-1, 16*jj) = bits`). All 23 failed with `--shim exact` too (soda: cgeist crash; 11 others: `member reference base type ... is not a structure` on `_BitInt` / `_Float16`; fixed_point_sqrt: `no matching function for call to 'fxp_sqrt'`). Corpus-wide the design study counted ~125 such lines in ~20 files (`~/hls-est-work/feas/A/design.md` section 11).
- **Why route A does not cover it:** a proxy is a pointer plus two ints, not a scalar wrapper; `--scalar-wrapper-abi` leaves it an LLVM struct, which hls-est cannot parse even if it compiled.
- **Options** (design.md section 11): (a) shim-side proxy `{T *p; int h, l;}` with `always_inline` members, relying on cgeist's inliner + mem2reg to remove the proxy alloca (untested; Polygeist mem2reg does not scalar-replace LLVM-struct allocas, so a struct memref probably survives); (b) keep the status quo (these designs report `cgeist error`); (c) an SROA for proxy-shaped struct memrefs in cgeist or hls-est. Rewriting the corpus sources is not an option (ground truth must be the untouched source). Recommendation: (a) as a time-boxed experiment, (b) until then.

## O14. A partial user unroll with factor F < trip < 2F loses its loop (filed 2026-10-09, T3 review fixes entry)
- **Symptom:** `loopUnrollByFactor` replaces a main loop left with a single iteration by its body, so `#pragma HLS unroll factor=4` on a 6-trip loop becomes six straight-line bodies: no loop carries `hls.unroll_partial`, nothing blocks the auto-pipelining of the parent, which is pipelined with the bodies in it (`test/hls-est/Passes/auto_pipeline_partial_epilogue.mlir` @single_main). Vitis keeps the exit checks in the unrolled body (UG1399 `skip_exit_check`), i.e. presumably a ceil(6/4) = 2-trip loop of 4 bodies, pipelined, with its parent not pipelined - unconfirmed, no kernel run. Related: when the cleanup loop of a non-dividing factor has a single iteration and its body holds an inner loop, that inner loop is decided on its own (pipelined) instead of being unrolled into the main loop's pipeline (@single_cleanup); its port demand per cycle is below the main pipeline's, so no BRAM effect is expected (unmeasured). No harness design is affected (the T3 review fixes left every subset total unchanged).
- **Fix:** a kernel pair (trip 6 / factor 4 and trip 9 / factor 4 with an inner loop, plus the loop tables) first; then unroll by F over ceil(N/F)*F iterations with the extra copies guarded (`affine.if`), if `--convert-affine-to-loopschedule` can schedule the guards, instead of MLIR's cleanup loop.

## O13. Floating-point invariant loads: the Vitis rule exists behind `float-loads-perfect`, off by default (filed 2026-10-09, T3 review fixes entry)
- **Symptom:** VITIS_NOTES.md N3 "Floating-point invariant loads": Vitis flattens a nest whose only imperfection is an inner-invariant load of a float element (8 kernels of `exp-src/pipeline_unroll_float`; polybench atax lp3/lp4, bicg lp1/lp2). - **Why not on by default:** Peter decides defaults (MEMOS.md M8). With the scalar shim `ap_fixed` is a float in MLIR while Vitis sees an integer, so the rule also changes decisions in ap_fixed designs, against N3: forgebench Llama_GPT_module, gpt_transformer_p1 and llama_transformer_p2 (totals unchanged). The rule is right only where MLIR's element type is the C type Vitis sees (float/double sources, or an integer-backed ap_fixed shim, MEMOS M3 route A). Subset totals with the option: atax and bicg move by 1 towards Vitis (no split), nothing else.

## O11. Replication at II > 1 depends on what the reads feed (filed 2026-10-09, T3 entry)
- **Symptom:** VITIS_NOTES.md N4 ("which II the copies are sized for"): with 16 reads of `la` per iteration and a final II of 8 forced by 16 stores of another array, Vitis builds 15 copies when the reads feed a dependent reduction (pu_impst_m8_n16, 30 BRAM; pu_red3c_l4_m4_n4 and pipeline_unroll_chk_4lvl at II 2) and none when each read feeds an independent store (pu_st_hoist_m8_n16, 4 BRAM). hls-est's final-II rule (`need = ceil((R+W)/II)`) gets pu_st_hoist and fir right and the other three wrong (4 / 14 / 14 vs 30); a `max(recurrence II, ceil((R+W)/17))` rule was tried in T3 and reverted (it gets the three right and pu_st_hoist wrong, 32 vs 4). `check_pipeline_unroll.py` BRAM column: 46/69 equal with the final-II rule.
- **Fix:** needs the criterion (probably the ASAP demand of the reads in the schedule: reads whose consumers chain are issued early with copies, reads consumed by independent stores are spread over the II); a kernel pair with the same R/W and II but the two dataflows, plus the `.adb` binding of `la`, would settle it. A loop whose recurrence runs through memory that `--auto-pipeline-unroll` could not promote (accesses under an `affine.if`, a non-affine index, a may-alias pair) is also sized as if its II were port-bound (O1).

## O5. cgeist hoists loop-invariant inner loops, which changes the structure Vitis decides on (filed 2026-10-09, T2 storage-model entry)
- **Symptom:** for `lp1(i) { lp2(j) { acc = 0; lp3(r < 8) { acc += alpha * buff_A[i][r]; } tmp[i][j] = acc; } }` cgeist (every `-O` level, `--raise-scf-to-affine`) emits `lp1 { %0 = affine.for r ... iter_args ; lp2(j) { store %0 } }`: the j-invariant reduction loop is hoisted out of lp2. Vitis makes its pipeline/flatten decision on the source structure (`lp1_lp2` flattened, `lp3` unrolled into it, 8 loads of buff_A per iteration -> 7 RAM_1WNR copies, 56 BRAM); on the hoisted structure the loads sit in a sequential body and no model can give more than one plain 8-BRAM RAM. The T2 validation therefore put the reduction loop back inside lp2 (`~/hls-est-work/t2/mlir_vitis/`, scratch script `t2_restructure.py`).
- **Where:** frontend (Polygeist); hls-est cannot undo it. Needs a cgeist flag or a sink pass before the pipeline decision (T3).

## O4. memref.global arrays are neither classified nor replicated (filed 2026-10-09, T2 storage-model entry)
- **Symptom:** `MemrefBankClassification::enumerateBanks` walks allocas only, so a `memref.get_global` result is "untracked" (2 scheduler slots), and `--bram-analysis` cannot attribute accesses to a `memref.global` (no SSA result), so it never replicates one and always prices it with one live port. VITIS_NOTES.md N1a: globals behave exactly like locals (same cores, same replication, same elimination). Every forgebench total is affected (its arrays are globals).
- **Fix:** classify and attribute through `get_global` uses (one entry per global, merged over its get_global sites), then the same rules as allocas.

## O3. Vitis uses both ports for independent reads in a non-pipelined body (filed 2026-10-09, T2 storage-model entry; after T3 it is part of the error of atax/bicg and the whole error of mvt)
- **After T3:** `tmp1[i] +=` is register-promoted by `--auto-pipeline-unroll` and tmp1 is 1 = Vitis; polybench atax 11 / bicg 12 / mvt 12 (no-split) differ from Vitis 13 / 14 / 14 by two arrays each. This issue covers atax buff_x, bicg buff_p and mvt buff_y1 / buff_y2 (Vitis 2 each, both ports of a sequential body). *Corrected by the T3 review:* atax buff_y_out and bicg buff_s_out are not O3 - Vitis flattens atax lp3/lp4 and bicg lp1/lp2 into one 4096-trip II-1 pipeline (float invariant load, VITIS_NOTES.md N3) where the array needs 1R + 1W per cycle, while hls-est's default decision unrolls the inner loop (O13). The earlier exact totals were the cancellation this entry already described.
- **Symptom:** hls-est charges a sequential (non-pipelined) scope one live port (`scopeDemand`, ii = 0), as T2 item 6 specified. Vitis schedules the 64 hoisted `buff_x[0..63]` reads of polybench/atax in the parent function with two ports: `buff_x_U` is `ram_2p`, 2 BRAM (replication.md R4 evidence `rep_atax_Ax_R64`, `results/vitis.json` polybench/atax memories); hls-est says 1. A read-modify-write chain in a sequential body still uses one port (load -> store dependence). The atax total is 13 either way only because `tmp1` errs the other way (Vitis register-promotes `tmp1[i] +=`, 1 BRAM; hls-est 2); that side now has a mechanism (`forward-stores`, O7), which is why the two must be adopted together.
- **Fix:** in sequential scopes count the independent accesses the body's DAG can issue in one cycle (min 2), or run the body through the list scheduler; then enable `forward-stores` (O7) in the same change and re-measure.

## O1. Loop-carried memory dependences never reach the modulo schedulers (filed 2026-10-09, review of 99ac05534, finding D1)
- **Symptom:** `a[i] = a[i-1] * k` (f32) schedules at II = 1 with both the simplex scheduler (`--convert-affine-to-loopschedule`) and the greedy one (`=fast-threshold=0`); the model's own recurrence bound is 6 (load 1 + mulf 4 + store 1). Only recurrences through `iter_args` are honoured (test/hls-est/Passes/fast_schedule_recurrence.mlir). The XFAIL lit test test/hls-est/Passes/memory_recurrence_xfail.mlir encodes the expected II and starts failing-as-XPASS when this is fixed.
- **Cause (pre-existing, inherited from upstream CIRCT's AffineToLoopSchedule):** `lib/Dialect/Resource/Passes/AffineToLoopScheduleModified.cpp` `runOnOperation` copies the analysis (`auto dependenceAnalysis = getAnalysis<MemoryDependenceAnalysis>();`) and `lowerAffineStructures` calls `replaceOp` on that copy when it lowers `affine.load`/`affine.store`/`affine.store_enable` to `memref.load`/`memref.store`/`hls.store_enable`. `lib/Dialect/Resource/Passes/CyclicSchedulingAnalysisModified.cpp` then reads the AnalysisManager's cached instance, whose keys are still the erased affine ops, so `getDependences(<lowered op>)` is always empty. The `replaceOp()` re-keying of 99ac05534 is correct but inert, and the grouped/memoized dependence analysis of that commit computes results nothing consumes (172 s of the ~390 s on forgebench/diff_orders_module).
- **What activating it costs (reviewer's experiment, reverted):** with `auto &dependenceAnalysis` the recurrences arrive on both schedulers (II 2 / 6 / 2 on `a[i] = a[i-1] + k` i32, the f32 case above, and its distance-3 variant), but 16 of the 42 test/hls-est/Estimation inputs then fail: "problem is infeasible" (polybench/atax, machsuite/nw, ...) and "multiple sinks detected" (basic/arraypartition_block, ...), because the intra-iteration (distance-0, including WAR/WAW) edges and the sink anchoring had never been exercised with real memory dependences. Canonical totals of polybench/atax, gesummv and polybench_pragmas/syr2k stayed 67 / 134 / 56 in that experiment.
- **Why it matters for Vitis matching:** a loop-carried memory dependence raises II, which lowers the per-bank port demand and can change the chosen RAM type and the x16/x32 aspect ratio. Activation is real work (dependence classes, anchoring) and needs its own totals check against the Vitis ground truth before it is adopted.
