## O27. cgeist drops a backward `goto`: the loop body runs once (filed 2026-10-10, cgeist O23 review fixes entry)
- **Symptom:** `o[0] = 0; int s = 0, i = 0; again: s = s * 3 + o[0]; o[0] = (o[0] + a[i]) & 65535; if (++i < 10) goto again; o[1] = s;` compiles without an error or a warning to straight-line code. The body runs once, and the `++i < 10` test and the branch back are gone. Output: `o[0] = a[0] & 65535`, `o[1] = 0`. Native clang gives `o[0]` 62715 where cgeist gives 12485 on the reviewer's input.
- **Scope:** older than O23 and unrelated to it. It happens in every binary checked (`cgeist.orig-hls-preserve-name`, cbc105e0, 18a550dd, c70ba2b0), with and without `--raise-scf-to-affine`, with `--scal-rep=0` and with `-O0`. The reproducer is the session scratchpad `o23v/probes/q1b_goto.cpp` (`v06_goto`, found by the O23 reviewer).
- **Corpus:** no kernel source under `tools/cgeist/Test/HLS` uses `goto`. The only matches are library headers (fmt, nlohmann json) of one hlsfactory class design. No harness design is affected as far as known.
- **Fix:** frontend (the cgeist codegen of `goto` / labels). Not started. If a fix is not quick, an error would be better than silently wrong code.

## O26. The scheduler offers a ROM (constant global) only two port slots per cycle, so `ROM_NP` is unreachable from affine input (filed 2026-10-10, W1a item 3 entry)
- **Symptom:** `MemrefBankClassification` tracks only allocas, so a `memref.get_global` bank gets the default two slots per cycle in `--convert-affine-to-loopschedule`. A 512x32 constant table read 3 or 4 times per iteration of an innermost loop is scheduled at II 2 with 2 reads per cycle and priced ROM_2P = 1 (`--bram-attribute-globals`); Vitis keeps II 1 and binds ceil(n/2) dual-port ROMs at x18 = 4 (`~/hls-est-work/experiments/fr_rom3r_w32_d512`, `fr_rom4r_w32_d512`; corpus aes `sbox` 8 reads -> 4, gsm `bitoff` 4 reads -> 2, N8 (c)). The pricing itself is right on lowered IR (lit `bram_formula_rom_ir.mlir`).
- **Fix (not started):** classify attributed read-only globals in `MemrefBankClassification` (no stores: replicable, ROM slots = 2 x the ROM copies; whether Vitis caps the copies like RAM_1WNR's 16 is unmeasured) together with M5 / decision #4 (globals attributed by default). Without `--bram-attribute-globals` (the default) a global is one RAM_1P whatever its reads (O4).

## O24. libm calls with constant arguments are not folded (exactclass `hls::sqrt` / `hls::exp` of a constant) (filed 2026-10-10, T8 entry)
- **Symptom:** the exactclass shim computes `hls::sqrt` / `hls::exp` of an `ap_fixed` through `__builtin_floor` / `__builtin_exp` on doubles; cgeist emits them as calls to external `@floor` / `@exp` (`func.func private @floor(f64) -> f64`), not as `math.floor` / `math.exp`, so even with constant arguments `--canonicalize --sccp` cannot fold them. Constants that Vitis folds stay computed in the MLIR: k_ctrl's `scale = 1.0 / hls::sqrt((data_t)4)` (Vitis 0.5 = raw 1024), probe out[3], [7], [10]-[12], [18] and probe2 out[5], [6], [20], [21] (`~/hls-est-work/t8/k/{probe,probe2,k_ctrl}.inl.mlir`). No BRAM effect seen (k_ctrl keeps Q and K either way, as Vitis), but a scale that is 0 only through such a call would not fold, and the arithmetic stays in the scheduled loops.
- **Fix:** cgeist: lower `__builtin_floor` / `__builtin_exp` (and the other C math builtins) to the math dialect as it does for the named C functions with floating arguments; or an hls-est fold of calls to the C math library on constants (a plain C-semantics fold). Not started.

## O23. cgeist forwards a store before a loop into a load inside it that the loop overwrites: the accumulation is lost (filed 2026-10-10, T7 c entry)

- **Fix:** frontend (Polygeist store-to-load forwarding across a loop that writes the location); a plain C-semantics fix, but /mnt/d/HLS/Polygeist is outside T7. Not started.
- **Status (2026-10-10, CHANGELOG "cgeist: no store-to-load forwarding across intervening writes (O23)"):** fixed in Polygeist 18a550dd, with review fixes in c70ba2b0 (CHANGELOG "cgeist: O23 review fixes"); **not yet installed**. ## O21. `--bram-seq-dual-port`'s stretch rule is not Vitis' list schedule: over-estimates with slack, under-estimates across independent loops (filed 2026-10-10, T6 entry; widened in the T6 review fixes entry)
- **Symptom:** VITIS_NOTES.md N12 "Exceptions". *Over-estimates:* sp_o_2st, sp_o_2ld_rmw, sp_o_far2 (two independent accesses before a variable-trip inner loop) and sp_stfar (a load and a store whose data comes from a 36-state urem) are 1 BRAM in Vitis (the two accesses issue in different states) and 2 with the option. The same pairs without slack share a state in Vitis (sp_2st, sp_far2, sp_o_ldst, sp_o_stld), and two loads feeding one consumer share it whatever the slack (sp_far, sp_o_far). *Under-estimate:* the stretch ends at every loop, but Vitis only keeps accesses on either side of a pipelined inner loop apart when the later one feeds something ordered after that loop (sp_split_loop, rv_sib3: 1). In rv_sib2 (`t = a[i]; s1 over t; u = a[i+32]; s2 over u`, s2 independent of s1) it starts the two outlined loops together and issues both loads in ST_3: `a` ram_2p 2, the option 1 (`test/hls-est/Passes/seq_scope_ports.mlir` `@sibling_loops` pins the 1). No harness-subset array is affected by either direction today as far as the per-array comparison shows (every subset change of the option is Vitis-exact per array or a shim-width difference, M6); an under-estimate of this kind would show as an array where Vitis has ram_2p and the option keeps RAM_1P.
- **Fix:** needs the criterion: a kernel series that moves one access along the slack (store vs load, consumer before / after the inner-loop call, 2 vs 3 independent accesses, a second loop that does / does not need the first one's result) and the state of each access in `sched_ports.py`. Vitis outlines a pipelined inner loop as a call inside the parent's basic block, moves ops across it and runs independent calls side by side, so a model needs the parent's list schedule, not the stretch rule. Hypothesis (unconfirmed): a load is placed in the state right before its first consumer starts, calls as early as their operands allow; it explains every load of N12 (sp_far, sp_split_loop, rv_sib2, rv_sib3, the sp_o_* loads) but not the stores (sp_o_ldst's store issues at its earliest state).

## O20. `--convert-affine-to-loopschedule` pipelines `hls.pipeline_off` innermost loops (filed 2026-10-10, T6 entry)

## O15. Assignable bit / range selects do not compile with the `exactclass` shim (filed 2026-10-10, route A entry)
- **Symptom:** `x.range(h, l) = v`, `x(h, l) = v`, `x[i] = b`, `(a, b) = v` are lvalue uses of Vitis' reference-proxy classes (`ap_range_ref {T& d_bv; int l, h;}`, `ap_bit_ref`, `ap_concat_ref`, `af_range_ref`). `shim/exactclass` returns `const` values from `range()` / `operator()` / `operator[]` / `bit()` / `operator,`, so these lines are clang errors (`no viable overloaded '='`), loudly instead of silently wrong. In the 7-dataset route-A run (`/tmp/routeA.json`) this stops **23 designs (14 with Vitis ground truth)**: all 11 soda (`dram_*_buf(255, 240) = Reinterpret<ap_uint<16>>(...)`), accelerators Mask-Net_dataset and SkyNet_dataset (`DATA.range(FM_RG + 16*c, 16*c) = d.range(FM_RG, 0)`), vitis_examples/01 fixed_point_sqrt (`fxp_sqrt.h:101 result.range(W2-1,0) = ap_uint<W2>(q >> 1)`), 9 class_ece8893_spring_2025 lab designs (`temp.range(16*(jj+1)-1, 16*jj) = bits`). All 23 failed with `--shim exact` too (soda: cgeist crash; 11 others: `member reference base type ... is not a structure` on `_BitInt` / `_Float16`; fixed_point_sqrt: `no matching function for call to 'fxp_sqrt'`). Corpus-wide the design study counted ~125 such lines in ~20 files (`~/hls-est-work/feas/A/design.md` section 11).
- **Why route A does not cover it:** a proxy is a pointer plus two ints, not a scalar wrapper; `--scalar-wrapper-abi` leaves it an LLVM struct, which hls-est cannot parse even if it compiled.
- **Options** (design.md section 11): (a) shim-side proxy `{T *p; int h, l;}` with `always_inline` members, relying on cgeist's inliner + mem2reg to remove the proxy alloca (untested; Polygeist mem2reg does not scalar-replace LLVM-struct allocas, so a struct memref probably survives); (b) keep the status quo (these designs report `cgeist error`); (c) an SROA for proxy-shaped struct memrefs in cgeist or hls-est. Rewriting the corpus sources is not an option (ground truth must be the untouched source). Recommendation: (a) as a time-boxed experiment, (b) until then.

## O14. A partial user unroll with factor F < trip < 2F loses its loop (filed 2026-10-09, T3 review fixes entry)
- **Symptom:** `loopUnrollByFactor` replaces a main loop left with a single iteration by its body, so `#pragma HLS unroll factor=4` on a 6-trip loop becomes six straight-line bodies: no loop carries `hls.unroll_partial`, nothing blocks the auto-pipelining of the parent, which is pipelined with the bodies in it (`test/hls-est/Passes/auto_pipeline_partial_epilogue.mlir` @single_main). Vitis keeps the exit checks in the unrolled body (UG1399 `skip_exit_check`), i.e. presumably a ceil(6/4) = 2-trip loop of 4 bodies, pipelined, with its parent not pipelined - unconfirmed, no kernel run. Related: when the cleanup loop of a non-dividing factor has a single iteration and its body holds an inner loop, that inner loop is decided on its own (pipelined) instead of being unrolled into the main loop's pipeline (@single_cleanup); its port demand per cycle is below the main pipeline's, so no BRAM effect is expected (unmeasured). No harness design is affected (the T3 review fixes left every subset total unchanged).
- **Fix:** a kernel pair (trip 6 / factor 4 and trip 9 / factor 4 with an inner loop, plus the loop tables) first; then unroll by F over ceil(N/F)*F iterations with the extra copies guarded (`affine.if`), if `--convert-affine-to-loopschedule` can schedule the guards, instead of MLIR's cleanup loop.

## O1. Loop-carried memory dependences never reach the modulo schedulers (filed 2026-10-09, review of 99ac05534, finding D1)
- **Symptom:** `a[i] = a[i-1] * k` (f32) schedules at II = 1 with both the simplex scheduler (`--convert-affine-to-loopschedule`) and the greedy one (`=fast-threshold=0`); the model's own recurrence bound is 6 (load 1 + mulf 4 + store 1). Only recurrences through `iter_args` are honoured (test/hls-est/Passes/fast_schedule_recurrence.mlir). The XFAIL lit test test/hls-est/Passes/memory_recurrence_xfail.mlir encodes the expected II and starts failing-as-XPASS when this is fixed.
- **Cause (pre-existing, inherited from upstream CIRCT's AffineToLoopSchedule):** `lib/Dialect/Resource/Passes/AffineToLoopScheduleModified.cpp` `runOnOperation` copies the analysis (`auto dependenceAnalysis = getAnalysis<MemoryDependenceAnalysis>();`) and `lowerAffineStructures` calls `replaceOp` on that copy when it lowers `affine.load`/`affine.store`/`affine.store_enable` to `memref.load`/`memref.store`/`hls.store_enable`. `lib/Dialect/Resource/Passes/CyclicSchedulingAnalysisModified.cpp` then reads the AnalysisManager's cached instance, whose keys are still the erased affine ops, so `getDependences(<lowered op>)` is always empty. The `replaceOp()` re-keying of 99ac05534 is correct but inert, and the grouped/memoized dependence analysis of that commit computes results nothing consumes (172 s of the ~390 s on forgebench/diff_orders_module; since T7 d1 it examines only the pairs inside one innermost loop, which are the ones an activation would need: conv_B 5.8M -> 170k pairs).
- **What activating it costs (reviewer's experiment, reverted):** with `auto &dependenceAnalysis` the recurrences arrive on both schedulers (II 2 / 6 / 2 on `a[i] = a[i-1] + k` i32, the f32 case above, and its distance-3 variant), but 16 of the 42 test/hls-est/Estimation inputs then fail: "problem is infeasible" (polybench/atax, machsuite/nw, ...) and "multiple sinks detected" (basic/arraypartition_block, ...), because the intra-iteration (distance-0, including WAR/WAW) edges and the sink anchoring had never been exercised with real memory dependences. Canonical totals of polybench/atax, gesummv and polybench_pragmas/syr2k stayed 67 / 134 / 56 in that experiment.
- **Why it matters for Vitis matching:** a loop-carried memory dependence raises II, which lowers the per-bank port demand and can change the chosen RAM type and the x16/x32 aspect ratio. Activation is real work (dependence classes, anchoring) and needs its own totals check against the Vitis ground truth before it is adopted.
