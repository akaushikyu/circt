## O37. cgeist wrong code: inside a loop, `r = f(&s); g(r)` with `g` taking `const T &` passes `f` applied twice (filed 2026-10-11, W8b check_semantics entry)
- **Symptom:** `check_semantics.py` finds forgebench/gpt_transformer_p1 different from its native build under both references (shim and real headers); the bisection with `--top-fn` narrows it to `dropout_8_32_ap_fixed_16_5_`: `unsigned r = lcg_rand(&seed); data_t rand_val = (data_t)r / (data_t)2147483647;` (the `ap_fixed` constructor takes `const T &`). In the MLIR, the loop body computes `lcg_rand`'s arithmetic twice: the first result is stored to `seed`, the second (lcg applied to the new seed) reaches the conversion.
- **Reproducer** (`~/hls-est-work/w8b2/probes/cref/q3.cpp`, plain C++): `unsigned f(unsigned *s) { *s = *s * 3u + 1u; return *s; }  struct W { int v; W(const unsigned &x) { v = (int)x; } };  void top(int out[8], unsigned seed) { for (int j = 0; j < 8; j++) { unsigned r = f(&seed); out[j] = W(r).v; } }`. cgeist c70ba2b0 stores `3 * s' + 1` (s' = the updated seed) to `out[j]` instead of `s'`. Correct without the loop (q4), with the reference bound by a plain `const unsigned &x = r` (q5), and with `--scal-rep=0` (the polygeist-affine-scalrep pass off). `check_semantics.py --probe q3.cpp --probe-top top` shows it.
- **Fix:** W8b, after its gate (a cgeist change): find the pass interaction (cgeist registers no MLIR IR-printing options; a polygeist-opt build can replay the pipeline), fix it, and add the probes as a cgeist lit test and a check_semantics probe.
- **Resolved 2026-10-12 (W8b, Polygeist 524525de):** `AffineBufferElimination` (Ops.cpp) forwarded the stored value to the load and computed the values it depends on again at the load when they were defined inside the loop, re-reading `seed` after the store. A value that dominates the load is now used as it is, and the overwrite check for a value computed again starts where it was first computed. Lit `Test/HLS/regressions/buffer-elim-remat-clobber.cpp` (q3).

## O1. Loop-carried memory dependences never reach the modulo schedulers (filed 2026-10-09, review of 99ac05534, finding D1)
- **Symptom:** `a[i] = a[i-1] * k` (f32) schedules at II = 1 with both the simplex scheduler (`--convert-affine-to-loopschedule`) and the greedy one (`=fast-threshold=0`); the model's own recurrence bound is 6 (load 1 + mulf 4 + store 1). Only recurrences through `iter_args` are honoured (test/hls-est/Passes/fast_schedule_recurrence.mlir). The XFAIL lit test test/hls-est/Passes/memory_recurrence_xfail.mlir encodes the expected II and starts failing-as-XPASS when this is fixed.
- **Cause (pre-existing, inherited from upstream CIRCT's AffineToLoopSchedule):** `lib/Dialect/Resource/Passes/AffineToLoopScheduleModified.cpp` `runOnOperation` copies the analysis (`auto dependenceAnalysis = getAnalysis<MemoryDependenceAnalysis>();`) and `lowerAffineStructures` calls `replaceOp` on that copy when it lowers `affine.load`/`affine.store`/`affine.store_enable` to `memref.load`/`memref.store`/`hls.store_enable`. `lib/Dialect/Resource/Passes/CyclicSchedulingAnalysisModified.cpp` then reads the AnalysisManager's cached instance, whose keys are still the erased affine ops, so `getDependences(<lowered op>)` is always empty. The `replaceOp()` re-keying of 99ac05534 is correct but inert, and the grouped/memoized dependence analysis of that commit computes results nothing consumes (172 s of the ~390 s on forgebench/diff_orders_module; since T7 d1 it examines only the pairs inside one innermost loop, which are the ones an activation would need: conv_B 5.8M -> 170k pairs).
- **What activating it costs (reviewer's experiment, reverted):** with `auto &dependenceAnalysis` the recurrences arrive on both schedulers (II 2 / 6 / 2 on `a[i] = a[i-1] + k` i32, the f32 case above, and its distance-3 variant), but 16 of the 42 test/hls-est/Estimation inputs then fail: "problem is infeasible" (polybench/atax, machsuite/nw, ...) and "multiple sinks detected" (basic/arraypartition_block, ...), because the intra-iteration (distance-0, including WAR/WAW) edges and the sink anchoring had never been exercised with real memory dependences. Canonical totals of polybench/atax, gesummv and polybench_pragmas/syr2k stayed 67 / 134 / 56 in that experiment.
- **Why it matters for Vitis matching:** a loop-carried memory dependence raises II, which lowers the per-bank port demand and can change the chosen RAM type and the x16/x32 aspect ratio. Activation is real work (dependence classes, anchoring) and needs its own totals check against the Vitis ground truth before it is adopted.
